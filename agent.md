# Контекст проекта
Приложение помогает офисным работникам и студентам делать регулярные двигательные паузы. Ключевые отличия от обычных таймеров:
- **Прогрессивная система уведомлений** (накапливает «долг здоровья», если пользователь игнорирует отдых).
- **Персонализация упражнений** под профиль здоровья пользователя.
- **Расчёт Health ROI** — показывает, сколько продуктивности и здоровья сохранил пользователь.
- **Уведомления работают вне окна сайта** (системные пуши, звук в фоне, мигание заголовка вкладки).

# Продуктовые фичи (обязательны к реализации)

## 1. State Machine «Долг здоровья»
Таймер сессии работает как конечный автомат с тремя уровнями срочности (`urgencyLevel`):

| Уровень | Триггер перехода | Время до следующего уведомления | Контент перерыва |
|---------|------------------|----------------------------------|------------------|
| 0 (Норма) | Старт сессии / кнопка «Отметился» | Базовое (52 мин) | 1–2 лёгких упражнения, 5 мин отдыха |
| 1 (Долг) | 5 мин игнора ИЛИ кнопка «Не могу» | Базовое × 0.6 (~31 мин) | 3 упражнения, 10 мин отдыха |
| 2 (Критический) | Повторный игнор на уровне 1 | Базовое × 0.3 (~15 мин) | 4–5 упражнений, 15 мин, жёсткий звук + вибрация |

**Правила:**
- При нажатии «Отметился» → сброс в уровень 0.
- При запросе упражнений из Supabase передавать `urgencyLevel` + `issue_id` пользователя.
- Максимальный уровень — 2 (дальше не растёт).

## 2. Уведомления вне окна
- **Web Notifications API** — системные пуши (проверять `Notification.permission`).
- **Web Audio API** — звуковой сигнал (не `<audio>`, он блокируется в неактивных вкладках).
- **Page Visibility API** — отслеживание активности вкладки.
- **document.title** — мигание текста «⏰ Пора отдохнуть! | Активные перерывы» когда вкладка неактивна.
- **Vibration API** — вибрация на мобильных для уровня 2.

## 3. Health ROI (метрика пользы)
Формула в конце сессии:
```
HealthScore = clamp((breaks_done × 15) − (breaks_missed × 25), 0, 100)
```
Отображать как прогресс-бар с текстом: *«Вы сохранили X% дневного ресурса»*.

## 4. Онбординг
Форма выбора «болевых точек» (шея, глаза, спина, запястья) → сохраняется в `localStorage` + в таблицу `user_profiles` Supabase.

# Обязательное ведение документации

Параллельно с кодом ты **обязан** поддерживать три файла. Без этого — потеря баллов за «Качество кода» (п. 4.2).

## 1. `PROGRESS.md` — Журнал прогресса
После каждой значимой задачи добавляй запись в начало файла:

```
### [ДД.ММ.ГГГГ ЧЧ:ММ] — [Название задачи]
- **Что сделано:** ...
- **Файлы изменены:** ...
- **Принятые решения:** ...
- **Проблемы и решения:** ... (если были)
- **Статус:** ✅ / ⚠️ / ❌
```

В конце файла веди **Summary**: количество выполненных задач, готовые фичи, backlog.

## 2. `ARCHITECTURE.md` — Архитектурные решения (ADR)
Только крупные решения. Формат:
- **Контекст** — проблема.
- **Решение** — что выбрали.
- **Альтернативы** — что отбросили и почему.
- **Последствия** — плюсы/минусы.

Темы: State Machine, Web Audio vs `<audio>`, схема БД, RLS для жюри, стратегия уведомлений.

## 3. `README.md`
Используй шаблон `README_TEMPLATE.md`. Раздел «Доступ к БД» — **первым**. Включи:
- Рабочую ссылку на Vercel.
- Инструкцию по доступу к БД (роут `/jury-db` + пароль).
- Инструкцию по быстрому тестированию (как ускорить таймер для проверки).
- Описание проверки клавиатурной навигации.
